Platform operator manual

Use this manual to operate the local storefront, custom admin, booking system, Strapi content, and Google Calendar connection.

Updated 22 October 2026 Local Docker Compose Not production-ready
Do not expose this installation to the public internet. It does not include production TLS, backups, monitoring, or public API abuse controls.

Lifecycle

Start and stop the platform

Run all commands from the repository root. Docker publishes application ports only on the local machine.

First start

  1. Install Docker Compose version 2 and Python 3.10 or later.
  2. Run the setup script.
sh setup.sh
  1. Enter the requested business information.
  2. Enter yes after you check the information.
  3. Create the first Strapi administrator when the script asks.
  4. Wait for the service health checks to finish.
The setup creates .env and config/business.json. Do not commit these files.

Start existing data

sh setup.sh --start-only

Check containers

docker compose ps

Read service logs

docker compose logs -f cms backend

Stop services

docker compose down

This command keeps the database and upload volumes.

Data removal: Do not run docker compose down -v unless you intend to remove persistent local data.

Identity

Sign in and permissions

The operations admin uses local Strapi administrator accounts. Google does not authenticate administrators.

  1. Open the operations admin.
  2. Enter the email and password for a Strapi administrator.
  3. Select Sign in.
STRAPI ADMIN

Content access

All Strapi administrators can open Content. Strapi Content Manager permissions control read and update access.

SUPER ADMIN

Platform administration

Only a Strapi Super Admin can use bookings, resources, connections, appearance, system checks, and other platform sections.

The backend checks the current Strapi account and roles before each protected request. A role change takes effect without a new platform deployment.

Five failed sign-in attempts for the same email and client address cause a five-minute lockout. A successful sign-in clears the failures.

Administrator sessions are stored in PostgreSQL. The default timeout is eight hours. Signing out also revokes the related Strapi device session.

Resources

Configure booking services

Services define the choices and durations that customers see in the storefront booking form.

Set customer booking

  1. Open Resources.
  2. Enable or disable Online appointments.
  3. Set the default duration from 5 through 480 minutes.
  4. Select Save settings.

Add a service

  1. Enter a service name with no more than 120 characters.
  2. Set a duration from 5 through 480 minutes in five-minute steps.
  3. Select Add service.

Use Save to change a service. Use Hide to remove it from new customer bookings. Use Activate to show it again.

A booking stores the service name and duration at creation time. Later service changes do not change historical bookings.

Calendar

Review booking operations

The weekly calendar shows confirmed and cancelled bookings across all resources.

  1. Open Bookings.
  2. Use the arrow controls to change the week.
  3. Select Today to return to the current week.
  4. Select a booking to open its details.
  5. Review the customer, service, resource, time, and calendar delivery state.
  6. Select Cancel booking when cancellation is required.
  7. Confirm the cancellation.

The customer email link opens the default email application. The platform does not send booking email.

The backend supports administrator creation and rescheduling APIs. The current admin UI does not expose these actions.

Calendar delivery states

State Meaning Operator action
SYNCED The provider accepted the latest booking change. No action is required.
PENDING The worker has not completed the delivery. Wait for the worker or select Sync now.
FAILED The delivery stopped after its retry limit. Check the connection, then select Sync now.
NOT_CONFIGURED No writable calendar mapping applies to the booking resource. Add or update a resource mapping if delivery is required.

Storefront

Customer booking flow

Customers can create a confirmed booking without an account.

  1. Open the storefront and select Book.
  2. Select a service when active services exist.
  3. Select a date and one of the displayed start times.
  4. Enter a customer name and valid email address.
  5. Submit the booking.

The backend calculates the end time from the service duration. If no active service exists, it uses the default duration.

A database lock prevents two customers from booking the same resource and time. If a conflict occurs, the customer must select another time.

Conditions for public booking

  • The administrator enabled customer booking.
  • At least one calendar provider has a writable mapping for the public resource.
  • Each mapped provider has a recent successful synchronization.
  • Provider authorization is valid.
  • No unresolved imported-calendar conflict exists.
Time-zone limit: The current storefront uses the customer browser time zone and fixed daily start times. It does not use business opening hours.

Storefront

Edit storefront pages

Home, Services, About, and Contact are editable in the admin. The storefront renders each page as an ordered list of sections.

Add or arrange sections

  1. Open Pages and select a page from the list.
  2. Select a section type to add it at the end of the list.
  3. Use the arrows to change the order. Select the delete icon to remove a section.

Heading

Show an eyebrow line and a title at the start of the page or after content.

Rich text

Write paragraphs, lists, and links with the formatting toolbar.

Image

Show an image from an address. Add a short caption below it.

Button and products

Point a button to another storefront page, or show shop products in the grid.

Edit rich text

Write in a Rich text section. Use Bold, Italic, Underline, List, and Link from the toolbar. When you save, the server removes markup that is not on the approved list.

Save a draft or publish

  1. Select Save draft. The change is stored and customers do not see it.
  2. Select Publish page. The storefront shows the new version at once.
The Live preview renders your current draft. Publishing makes that content visible on the matching storefront page. A page without published content keeps its built-in layout.

Storefront

Languages and color palette

The Appearance section controls the customer website. Saved changes apply to every visitor after you save them.

Enable or disable a language

  1. Open Appearance.
  2. Select the checkbox for a language to enable it, or clear it to disable it.
  3. The change saves at once. The storefront language switcher updates immediately.

The platform supports German, English, Russian, and Turkish. A visitor sees the saved choice first, then a matching browser language, then the first enabled language. Keep at least one language enabled; the admin blocks the last switch-off.

Publish a color palette

  1. Open Appearance.
  2. Select a palette card: Maison, Noir, Lagoon, or Blush.
  3. The selection publishes at once and applies to every storefront visitor.
Translations cover the storefront interface: navigation, buttons, booking, shop, cart, checkout, and footer. Page content that you write in the page editor stays in its authored language. The personal admin theme at the bottom of the section applies to this browser only.

Commerce

Run the shop

Open Commerce in the admin. The status bar shows whether a payment provider is connected and whether the shop accepts orders.

Create a product

  1. Open the Products tab.
  2. Enter a slug, a name, and an optional description.
  3. Add at least one option with a SKU, a label, a price in euros, and a stock count.
  4. Select Create product. The shop shows the product immediately.

Select an existing product to edit its name, description, and options. Saving replaces the full option set. Deleting a product removes it from the shop. Completed orders keep their stored product details.

Set sales rules

  1. Open the Settings tab.
  2. Turn the shop on or off for customers.
  3. Set the tax rate, the flat shipping cost, and an optional free-shipping threshold.
The server calculates subtotal, tax, shipping, and total at checkout. Amounts sent by a browser do not apply. Prices are stored as euro minor units.

Customer cart and stock limits

  • The browser stores the anonymous cart in local storage.
  • A product page shows the quantity that is already in the cart.
  • Product and cart quantity controls do not accept more than the displayed stock.
  • If stock decreases, the storefront reduces an old cart quantity and shows a warning.
  • Adding an item to the browser cart does not reserve stock.
  • The server checks and reserves stock when it creates the pending order.

A successful checkout clears the cart display and old warnings. The confirmation page shows the order number and the payment action when payment is required.

Each new order has a private access token. Stripe returns the customer to a link that keeps this token in the browser URL fragment. The storefront sends it only in the X-Order-Access-Token request header. Do not share the order link.

Order lifecycle

  1. PENDING_PAYMENT — the server holds stock for the order.
  2. PAID — payment confirmed, by Stripe webhook or manual action. The stock remains reserved until fulfillment or refund.
  3. FULFILLED — you ship with a carrier and tracking number. Physical stock decreases.
  4. CANCELLED — an unpaid order closes, or a paid order receives a refund. Shipped items return to stock.

Work an order

Select an order in the list, then use the actions available for its status:

  • Mark paid — confirm a manual payment without Stripe.
  • Cancel order — close an unpaid order and release its stock hold.
  • Fulfill order — record the carrier and tracking number, then deduct stock.
  • Refund order — refund a paid or shipped order once. Shipped items return to stock.

Connect Stripe

The platform needs two values from your Stripe account: a secret API key and the webhook signing secret for one endpoint. Both come from the dashboard at dashboard.stripe.com. Select either the test or the live environment in the top bar before you copy a value; the keys are different for each. Use the test environment until production is verified.

Get the secret key (STRIPE_SECRET_KEY)

  1. In the Stripe dashboard, select Developers in the left navigation, then select API keys. If you do not see it yet, create your first test key.
  2. Select Standard secrets. Copy the secret key that starts with sk_test_, or sk_live_ for production.
  3. Paste it into .env as STRIPE_SECRET_KEY=sk_.... Do not commit the key to version control.

Get the webhook secret (STRIPE_WEBHOOK_SECRET)

  1. In the dashboard, select Developers, then Webhooks.
  2. Select Add endpoint.
  3. Set the callback URL to your public backend address plus the path /webhooks/stripe. For a local run use the Stripe CLI forwarder described below, and keep this endpoint for production.
  4. Select Add another event and add these events:
  • checkout.session.completed
  • checkout.session.async_payment_failed
  1. Select Add endpoint to save it.
  2. Open the new endpoint and select Show next to the signing secret.
  3. Copy the value that starts with whsec_. Paste it into .env as STRIPE_WEBHOOK_SECRET=whsec_.... The platform verifies each event against this secret and rejects events without a valid signature.

Apply the configuration

  1. Restart with docker compose up -d --build backend.
  2. Confirm the platform reports Stripe as configured: GET /api/v1/admin/commerce/status must return {"stripeConfigured": true}.

Local testing with the Stripe CLI (step by step)

A webhook is a message that Stripe sends to your app. On a home or office network your computer has no public address, so Stripe cannot reach it directly. The Stripe CLI solves this: you run one small program on your computer, and it opens a private tunnel that forwards every test event from Stripe into your running platform. Everything below uses test mode, so no real money moves.

Step 1 — Install the Stripe CLI

Install it once with the command that matches your computer.

  • macOS (Apple chip or Intel)
brew install stripe-cli   # if "brew" is missing, run: /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
  • Ubuntu or Debian (Linux)
sudo curl -sSfL https://stripe.install.sh | sudo bash
  • Windows 10 or 11 (PowerShell)
winget install --id Stripe.stripe-cli   # if "winget" is missing, use: irm https://stripe.dev/install.ps1 | iex

If none of those fit your system, open the download page in a browser:

  • https://docs.stripe.com/stripe-cli#installation

Step 2 — Check the install worked

stripe --version

You must see a version number (for example, stripe-cli version 1.23.0). If you see "not found" or "nicht erkannt", close the terminal window and open a new one; if that still fails, install it again from Step 1.

Step 3 — Log in to your Stripe account

stripe login

This opens a page in your browser where you allow the CLI to connect to your Stripe test account. After it finishes, run this and read the result: 

stripe config --list
  • A line that starts with api_key is shown (for example, a value beginning with sk_test_...567890).

Step 4 — Start the local listener

Keep this command running in its own terminal window while you test. It must stay open: when it closes, forwarding stops. 

stripe listen --forward-to http://storefront.localhost/webhooks/stripe \
  --events checkout.session.completed,checkout.session.async_payment_failed
Newer CLI versions refuse to start without an event list and print "must specify events to forward using --events, --all-snapshot, or --all-thin". The command above lists exactly the two events this platform processes. Use --all-snapshot only when you want every test event forwarded. Older CLI versions also accept the shorter form without --events.
The platform backend, Storefront, and Traefik must be running before you use the checkout link. The Storefront proxy sends the webhook to the private Backend service.

Step 5 — Read the signing secret from the listener

Right after it starts, the listener prints text like this:

Listens to localhost:3000 and forwards to http://storefront.localhost/webhooks/stripe

    Listening... (press CTRL+C to quit)

    Add webhook endpoint with secret:  whsec_1a2b3c4d5e6f7g8h9i0j
    Endpoint ID:                      whpay_00000000000000

Copy the value that starts with whsec_. This is your local STRIPE_WEBHOOK_SECRET. Put it in .env, then restart the backend so it reads the new value: 

# .env  (replace with YOUR whsec_... from the listener)
STRIPE_WEBHOOK_SECRET=whsec_YOUR_VALUE_FROM_THE_LISTENER
docker compose up -d --build backend

Step 6 — Make a test purchase

  1. In the storefront, add a product to the basket and start checkout.
  2. Open the Stripe payment page in the browser it gives you.
  3. Use this test card (it always succeeds):
  • Card number: 4242 4242 4242 4242
  • Expiry date: any future month, for example 12/30
  • CVC: any 3 digits, for example 123
  1. Complete the payment.
  2. Watch your listener window. You must see a green line like: POST /webhooks/stripe ... 200 OK. This proves Stripe reached your app and it accepted the event.

Step 7 — Confirm the order is paid

Open the operations admin, then open the same order in Commerce. Its status must have changed from PENDING_PAYMENT to PAID by itself, without you selecting Mark paid. That change is made automatically by the verified webhook.

Step 8 — Stop when finished

CTRL+C

Press this inside the listener window to stop forwarding.

Keep test and live separate. The whsec_... from a local listener is for test events only, and it changes each time you run stripe listen. When you move to production, create the real webhook endpoint in the dashboard (see Get the webhook secret) and use that permanent signing secret instead.

If something goes wrong

  • "not found" when you type stripe: open a new terminal window; if it still fails, redo Step 1.
  • The listener refuses to start: make sure Traefik, Storefront, Backend, and PostgreSQL are running with docker compose up -d, then run the listener again.
  • "forwarding failed" or "connection refused": run docker compose ps. The required containers must be healthy. If the Backend is not healthy, restart it with docker compose up -d --build backend.
  • The order stays PENDING_PAYMENT: re-read the signing secret (Step 5), put it in .env, and restart the backend. Then repeat Step 6.
Without STRIPE_SECRET_KEY the platform runs in manual mode. Orders stay in PENDING_PAYMENT until you select Mark paid. The Stripe CLI is only needed so that test webhooks can reach a local computer; it is not required for production, where the dashboard endpoint sends events directly.

Operations analytics

Reports and monitoring

Use the Reports section to review sales, revenue, orders by status, low stock, and booking volume. All amounts are EUR. All dates follow UTC.

View operational reports

  1. In the admin panel, select Reports in the side navigation.
  2. Select a date range or choose Last 7 days, Last 30 days, or Last 90 days.
  3. Review the KPI cards: paid orders, gross revenue, cancelled orders, units sold, bookings, and refunded amount.
  4. Use the daily trend table to compare activity over time. The sales funnel shows order counts by status.
  5. Check inventory alerts for variants with the lowest available stock.

Export data

Select a CSV button to download trend rows, inventory alerts, or the order ledger. The order ledger includes customer name and email address. Store exports securely and delete them when you no longer need them. Follow your organization's data retention policy.

Scrape metrics with Prometheus

The backend exposes metrics at /actuator/prometheus on the private Compose network. Point a Prometheus or Grafana sidecar at this address:
http://backend:8080/actuator/prometheus
Business counters include order creation, payment confirmation, fulfilment, refunds, and out-of-stock checkout failures. JVM, HTTP, and system meters are available as well. The endpoint requires no sign-in because it contains no customer data.

Interpret the figures

Reports read the same tables that store orders and bookings, so they match the order ledger. Use them to understand activity. Before you use a report for a financial decision, reconcile it with your accounting records. Time ranges are half-open intervals in UTC: a range starts at 00:00 on the first day and ends before midnight on the last day.

Connections

Operate Google Calendar

Google OAuth grants Calendar and Gmail send access. It is separate from the Strapi administrator session and does not grant mailbox read access.

Connect the account

  1. Configure the Google OAuth client as described in Google OAuth setup.
  2. Sign in to the operations admin as a Strapi Super Admin.
  3. Open Connections.
  4. Select Connect Google services.
  5. Approve the requested Calendar permissions at Google.

Map a resource

  1. Enter the exact platform resource ID.
  2. Select a writable Google calendar.
  3. Select Send bookings to Google when the platform must publish booking events.
  4. Select Save mapping.

Saving a mapping starts synchronization. The default worker interval is 60 seconds. The first import looks back 31 days.

Imported busy events block new bookings. Cancelled, transparent, invalid, and platform-managed events do not create busy blocks.

Calendar conflict: An imported event can overlap an existing confirmed booking. The mapping changes to CONFLICT, and public booking stops until an operator resolves the conflict.

Run or remove the connection

  • Select Sync now to import changes, deliver due booking changes, and requeue failed deliveries.
  • Select Remove to delete one resource mapping and its provider data.
  • Select Disconnect to revoke the grant and remove local Google connection data.
Signing out does not disconnect Google. Disconnecting Google does not sign out the administrator.

Strapi

Edit the Business Profile

The custom admin uses your Strapi permissions to read and update the Business Profile single type.

  1. Open Content.
  2. Edit the name, slug, email, time zone, locale, currency, phone, or address.
  3. Select Save content.

If the page reports a permission error, update the administrator role in Strapi. Grant the required Business Profile read and update actions.

The storefront does not currently read the Business Profile. The profile has no draft-and-publish workflow.

Maintenance

Check and protect the system

Configuration checks show whether required values exist. They do not prove that each external service works.

Backend health

docker compose exec backend curl -fsS http://127.0.0.1:8080/actuator/health

The response must contain "status":"UP".

Container health

docker compose ps backend admin cms postgres

Each required service must report healthy.

Rebuild application services

docker compose up -d --build --force-recreate backend admin

Use this command after an authentication or integration configuration change.

Validate Compose

docker compose config --quiet

No output means that Compose accepted the configuration.

Wipe all data and start clean

docker compose down -v
rm -f .env config/business.json .setup-state.json
sh setup.sh

This removes the databases, uploads, company details, and generated secrets. Your Google Cloud client ID and secret stay valid.

Data reset only

docker compose down -v
rm -f .setup-state.json
sh setup.sh

This keeps the company details and existing secrets.

Protect these items

  • The PostgreSQL pgdata volume.
  • The Strapi cmsuploads volume.
  • The private .env file.
  • The config/business.json file.
  • The Strapi and OAuth token encryption keys.
Backup gap: The repository does not provide an automated backup or restore process. Do not claim production readiness until restore tests pass.

Recovery

Troubleshoot common problems

Check the reported condition before you change code or delete data.

The operations admin rejects my credentials

Confirm that the account exists in Strapi. Use the Strapi administrator email and password. Wait five minutes after repeated failures.

I can open Content but no other section

The account is not a Strapi Super Admin. Assign the strapi-super-admin role when full platform access is required.

Content reports a permission error

Open Strapi role settings. Grant the required Business Profile read or update action.

Google reports redirect_uri_mismatch

Register exactly http://localhost/login/oauth2/code/google. Do not add a trailing slash. The backend must send the same URI: set PLATFORM_ADMIN_BASE_URL=http://localhost in the local environment file.

The Google connection reports an error

Check the Calendar API, OAuth consent, and stored encryption key. Reconnect the account if authorization is no longer valid.

Public booking is unavailable

Enable customer booking. Add a writable mapping for the public resource. Run synchronization and resolve each mapping conflict.

A booking shows NOT_CONFIGURED

Add a writable calendar mapping for that booking resource. A mapping for a different resource does not apply.

The backend cannot decrypt saved tokens

Restore the original encryption key. If the key is lost, remove the unusable connection data and complete authorization again.

Release status

Current implementation limits

These limits are part of the current development preview.

SECURITY

No public deployment controls

TLS ingress, secure production defaults, rate limits, bot protection, and security verification are incomplete.

OPERATIONS

Limited recovery automation

Operational reports and Prometheus metrics are available. Automated backups, restore tests, alerting rules, and high availability are not implemented.

BOOKING

Limited schedule model

The storefront uses fixed times. Customer cancellation, customer rescheduling, and business opening hours are not implemented.

COMMERCE

Limited commerce operations

Refunds close a whole order at once. Product image upload, customer order email, order reports, and CSV export are available. Partial refunds and returns are not implemented.

MAIL

Limited email delivery

Gmail and SMTP delivery are available for form receipts and order confirmations. Booking mail, a durable notification outbox, bounce handling, and Microsoft Graph Mail are not implemented.

CONTENT

Limited storefront content

Storefront pages render editor sections only after you publish them. Pages without published content fall back to the built-in layout. Product images come from addresses entered in the page editor or product options, not from a media library.

Read implementation status, implementation backlog, and extension architecture before release planning.
